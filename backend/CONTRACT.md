# Контракт блока backend

Сюда вписывай ручки, которые твой блок отдаёт наружу. Соседи по команде
видят только этот файл — не код. Если ручка изменилась или появилась новая —
обнови этот файл, иначе сосед о ней не узнает.

## Что я отдаю наружу

### GET /health
Проверка живости. Возвращает `{status, team, block, commit, clients_loaded,
transactions_loaded}`.

### GET /clients
Список клиентов команды. Параметры запроса (все опциональные):
- `segment` — строка, сегмент клиента;
- `has_overdue` — bool, был ли просрочен платёж;
- `min_income` — int, минимальный доход в рублях;
- `limit` — int, ограничение по числу записей (по умолчанию 50, максимум 500).

Возвращает `{total, items: [клиенты]}`. Клиент — JSON с полями из seed:
`id, name, segment, balance_rub, income_rub, has_overdue_history` и другими.

### GET /clients/{client_id}
Полная карточка одного клиента. Возвращает объект клиента. `404`, если не найден.

### GET /transactions/{client_id}
Транзакции клиента, новые сверху. Параметры: `limit` (по умолчанию 20).
Возвращает `{total, items: [транзакции]}`. Транзакция —
`{id, client_id, type, amount_rub, ts, counterparty}`.

### POST /api/transfer
Перевод средств между клиентами команды. Принимает JSON
`{from_client_id, to, amount_rub}`. `to` — это либо id клиента, либо часть
имени получателя (поиск по подстроке). Возвращает `{status, kind
(internal|external), amount_rub, to, from_client_id, new_balance_rub, tx_id, ts}`.

## План кредитной функции

Цель: клиент подаёт заявку на кредит в retail, CIB автоматически принимает
решение по данным клиента, а retail показывает результат и причину решения.
Общая папка команды не используется; этот план и изменения интерфейсов
фиксируются в контрактах блоков.

### Этап 0. Согласовать правила

1. Продукт: сумма от 50 000 до 1 500 000 ₽, срок от 6 до 60 месяцев.
2. Базовая ставка: от 17,9% для низкого риска до 24,9% для остальных;
   оформление и досрочное погашение без комиссии.
3. Платёж ограничить примерно одной третью подтверждённого дохода.
4. Отклонять заявки при серьёзной действующей просрочке. CIB использует
   доход, сегмент, баланс и историю просрочек клиента из backend; если для
   определения действующей просрочки нужна отдельная характеристика, её
   сначала добавить в данные backend и контракт.
5. Зарплатным и постоянным клиентам разрешить скидку 2–3 процентных пункта
   и заранее рассчитывать доступный лимит.
6. Первая версия возвращает `approved` или `rejected`, понятный `reason_code`,
   одобренную сумму, срок и персональную ставку.

### Этап 1. Backend — заявки и хранение

1. Добавить модель заявки с полями `id`, `client_id`, `amount_rub`,
   `term_months`, `status`, `decision`, `reason_code`, `reason`,
   `approved_amount_rub`, `approved_term_months`, `personal_rate_pct`,
   `monthly_payment_rub`, `created_at` и `updated_at`.
2. Добавить `POST /credit-applications` для создания заявки. Проверять,
   что клиент существует, сумма и срок положительные; новая заявка получает
   статус `pending`.
3. Добавить `GET /credit-applications/{application_id}` для чтения заявки.
4. При изменении интерфейсов сразу дописать точные поля ответа в этот
   контракт и сообщить об этом retail и cib.

### Этап 2. CIB — решение

1. Получить из backend заявку и карточку клиента по согласованным запросам.
2. Реализовать единое правило решения без скрытых условий: результат
   `approved` или `rejected`, код причины и пояснение для клиента.
3. Добавить внутренний запрос CIB для принятия решения по
   `application_id` и обновления статуса заявки в backend.
4. Описать в `cib/CONTRACT.md` вход, ответ, коды причин и ошибки.

### Этап 3. Retail — путь клиента

1. Добавить форму суммы и срока с проверкой обязательных полей.
2. Добавить `POST /api/credit-applications`, который запускает создание
   заявки и решение CIB, не дублируя данные клиента в retail.
3. Добавить `GET /api/credit-applications/{application_id}` для показа
   статуса и результата.
4. Показать клиенту решение, сумму, срок и понятную причину отказа.
5. Описать новые запросы в `retail/CONTRACT.md`.

### Этап 4. Сквозная проверка

1. Проверить одобряемого клиента: заявка создана, решение сохранено,
   retail показывает результат.
2. Проверить отказ по каждому согласованному коду причины.
3. Проверить неизвестного клиента, нулевую сумму, отрицательный срок и
   повторное чтение заявки.
4. Проверить, что retail не хранит собственную копию данных клиента, CIB
   получает данные через backend, а все три контракта совпадают.
5. После проверки сохранить изменения блоков в общую копилку и проверить
   опубликованный сценарий клиента.
