# Контракт блока backend

Сюда вписывай ручки, которые твой блок отдаёт наружу. Соседи по команде
видят только этот файл — не код. Если ручка изменилась или появилась новая —
обнови этот файл, иначе сосед о ней не узнает.

## Что я отдаю наружу

### GET /health
Проверка живости. Возвращает `{status, team, block, commit, clients_loaded,
transactions_loaded}`.

### GET /clients
Список клиентов команды. Параметры запроса (все опциональные):
- `segment` — строка, сегмент клиента;
- `has_overdue` — bool, был ли просрочен платёж;
- `min_income` — int, минимальный доход в рублях;
- `limit` — int, ограничение по числу записей (по умолчанию 50, максимум 500).

Возвращает `{total, items: [клиенты]}`. Клиент — JSON с полями из seed:
`id, name, segment, balance_rub, income_rub, has_overdue_history` и другими.
Для кредитного сценария карточка также содержит `monthly_income_rub` (равен
`income_rub`), `is_loyal_client` (true после 12 календарных месяцев с
`joined_at`), `risk_level`, `has_serious_current_overdue` и
`is_payroll_client`. Последние три поля возвращаются `null`, пока для них
нет подтверждённых исходных данных или согласованного правила; историю
просрочек нельзя трактовать как текущую просрочку.

### GET /clients/{client_id}
Полная карточка одного клиента, включая кредитные поля, описанные выше.
Возвращает объект клиента. `404`, если не найден.

### GET /transactions/{client_id}
Транзакции клиента, новые сверху. Параметры: `limit` (по умолчанию 20).
Возвращает `{total, items: [транзакции]}`. Транзакция —
`{id, client_id, type, amount_rub, ts, counterparty}`.

### POST /api/transfer
Перевод средств между клиентами команды. Принимает JSON
`{from_client_id, to, amount_rub}`. `to` — это либо id клиента, либо часть
имени получателя (поиск по подстроке). Возвращает `{status, kind
(internal|external), amount_rub, to, from_client_id, new_balance_rub, tx_id, ts}`.

### POST /crypto-topups
Создаёт учебное пополнение USDT. Принимает `{client_id, amount_rub}`; сумма
должна быть от 1 000 до 100 000 ₽. Backend сам запрашивает котировку CIB
через `POST /crypto/quote` и не доверяет курсу или суммам из браузера.
Возвращает `{id, client_id, amount_rub, credit_amount_rub, crypto_amount,
rate_rub_per_unit, fee_rub, expires_at,
status, demo_only, created_at, updated_at, transaction_id, credited_at}` со
`status: pending` и `demo_only: true`. Поля котировки сохраняются в формате
CIB: `crypto_amount`, `credit_amount_rub`, `rate_rub_per_unit` и `fee_rub` —
десятичные строки.
Котировка должна иметь нулевую комиссию и будущий срок действия; недоступность
CIB возвращается как `503`, недействительная котировка — как `502`.

### GET /crypto-topups/{topup_id}
Возвращает сохранённое учебное пополнение по идентификатору. `404`, если оно
не найдено.

### POST /crypto-topups/{topup_id}/simulate-confirm
Однократно моделирует зачисление рублей на учебный баланс клиента по
действующей котировке. При успехе возвращает пополнение со `status: credited`,
`transaction_id` и `new_balance_rub`; операция записывается с типом
`crypto_topup_demo` и `demo: true`. Повторный запрос возвращает тот же результат
без повторного начисления. Просроченная котировка получает `status: expired` и
возвращает `409`; реальные адреса кошельков и настоящие переводы не используются.

### POST /credit-applications
Создаёт кредитную заявку. Принимает JSON
`{client_id, amount_rub, term_months}`. Сумма — от 50 000 до 1 500 000 ₽,
срок — от 6 до 60 месяцев. Возвращает заявку со `status: pending` и полями
`{id, client_id, amount_rub, term_months, status, decision, reason_code,
reason, approved_amount_rub, approved_term_months, personal_rate_pct,
monthly_payment_rub, created_at, updated_at}`. `404`, если клиент не найден;
`400`, если сумма, срок или формат запроса неверны.

### GET /credit-applications/{application_id}
Возвращает кредитную заявку по идентификатору со всеми полями заявки.
`404`, если заявка не найдена.

### PATCH /credit-applications/{application_id}/decision
Записывает решение CIB. Принимает JSON
`{decision, reason_code, reason, approved_amount_rub,
approved_term_months, personal_rate_pct, monthly_payment_rub}`. `decision` —
`approved` или `rejected`. Для одобрения обязательны одобренная сумма, срок,
персональная ставка от 14,9% до 24,9% включительно и положительный
ежемесячный платёж. Базовые ставки продукта — 17,9% для низкого риска и
24,9% для остальных; скидки зарплатным и постоянным клиентам не суммируются,
применяется большая скидка (2 или 3 процентных пункта). Повтор той же записи
возвращает сохранённое решение без изменения времени обновления; попытка
изменить принятое решение возвращает `409 decision_conflict`.
Возвращает заявку со `status: decided`. `404`, если заявка не найдена;
`400`, если решение или его параметры неверны.

### Данные для кредитного решения

- `income_rub` подтверждён как месячный доход; отдельный `income_verified`
  не нужен.
- `risk_score` в учебных данных находится в диапазоне 0,041–0,669. Большее
  значение связано с большим риском; `risk_level=low` вычисляется при
  `risk_score <= 0,20` включительно, выше возвращается `standard`.
- `is_loyal_client` вычисляется как не менее 12 календарных месяцев с
  `joined_at`.
- Источника подтверждённого зарплатного статуса нет: `is_payroll_client` —
  `null`. Зарплатная скидка отключена, и `null` не блокирует решение CIB;
  скидка постоянному клиенту остаётся 3 процентных пункта.
- Для совместной проверки добавлены явно обозначенные учебные значения
  текущей просрочки: `c-01004` — `true` (серьёзная текущая просрочка),
  `c-01000` — `false` (серьёзной текущей просрочки нет). Это демонстрационные
  данные, созданные для тестового сценария, а не сведения из реального
  источника. Для всех остальных клиентов `has_serious_current_overdue` —
  `null`; `has_overdue_history` не заменяет текущую просрочку.

## План кредитной функции

Цель: клиент подаёт заявку на кредит в retail, CIB автоматически принимает
решение по данным клиента, а retail показывает результат и причину решения.
Общая папка команды не используется; этот план и изменения интерфейсов
фиксируются в контрактах блоков.

### Этап 0. Согласовать правила

1. Продукт: сумма от 50 000 до 1 500 000 ₽, срок от 6 до 60 месяцев.
2. Базовая ставка: 17,9% для низкого риска и 24,9% для остальных; оформление
   и досрочное погашение без комиссии. Персональная ставка после скидки — от
   14,9% до 24,9% включительно.
3. Платёж ограничить примерно одной третью подтверждённого дохода.
4. Отклонять заявки при серьёзной действующей просрочке. CIB использует
   доход, сегмент, баланс и историю просрочек клиента из backend; если для
   определения действующей просрочки нужна отдельная характеристика, её
   сначала добавить в данные backend и контракт.
5. Зарплатным клиентам разрешить скидку 2 процентных пункта, постоянным —
   3 процентных пункта; скидки не суммируются, применяется большая. Для этих
   клиентов заранее рассчитывать доступный лимит.
6. Первая версия возвращает `approved` или `rejected`, понятный `reason_code`,
   одобренную сумму, срок и персональную ставку.

### Этап 1. Backend — заявки и хранение (реализовано)

1. Реализована модель заявки с полями `id`, `client_id`, `amount_rub`,
   `term_months`, `status`, `decision`, `reason_code`, `reason`,
   `approved_amount_rub`, `approved_term_months`, `personal_rate_pct`,
   `monthly_payment_rub`, `created_at` и `updated_at`.
2. Реализован `POST /credit-applications` для создания заявки. Проверяет,
   что клиент существует, сумма и срок положительные; новая заявка получает
   статус `pending`.
3. Реализован `GET /credit-applications/{application_id}` для чтения заявки.
4. Реализован `PATCH /credit-applications/{application_id}/decision` для
   записи решения CIB; точные поля ответа указаны выше.
5. При изменении интерфейсов сразу дописывать точные поля ответа в этот
   контракт и сообщить об этом retail и cib.

### Этап 5. Учебное USDT-пополнение (реализовано)

1. Backend принимает только сумму в рублях, получает котировку CIB и сохраняет
   её срок действия, курс, условные USDT и нулевую комиссию.
2. Backend выполняет одноразовое учебное зачисление и пишет демонстрационную
   операцию; повтор не начисляет деньги повторно.
3. Retail подключается после публикации CIB-калькулятора и проверяет успешное
   пополнение, повтор, истечение срока, неверную сумму и недоступность CIB.

### Этап 2. CIB — решение

1. Получить из backend заявку и карточку клиента по согласованным запросам.
2. Реализовать единое правило решения без скрытых условий: результат
   `approved` или `rejected`, код причины и пояснение для клиента.
3. Добавить внутренний запрос CIB для принятия решения по
   `application_id` и обновления статуса заявки в backend.
4. Описать в `cib/CONTRACT.md` вход, ответ, коды причин и ошибки.

### Этап 3. Retail — путь клиента

1. Добавить форму суммы и срока с проверкой обязательных полей.
2. Добавить `POST /api/credit-applications`, который запускает создание
   заявки и решение CIB, не дублируя данные клиента в retail.
3. Добавить `GET /api/credit-applications/{application_id}` для показа
   статуса и результата.
4. Показать клиенту решение, сумму, срок и понятную причину отказа.
5. Описать новые запросы в `retail/CONTRACT.md`.

### Этап 4. Сквозная проверка

1. Проверить одобряемого клиента: заявка создана, решение сохранено,
   retail показывает результат.
2. Проверить отказ по каждому согласованному коду причины.
3. Проверить неизвестного клиента, нулевую сумму, отрицательный срок и
   повторное чтение заявки.
4. Проверить, что retail не хранит собственную копию данных клиента, CIB
   получает данные через backend, а все три контракта совпадают.
5. После проверки сохранить изменения блоков в общую копилку и проверить
   опубликованный сценарий клиента.
